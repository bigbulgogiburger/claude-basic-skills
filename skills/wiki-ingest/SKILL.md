# wiki-ingest — 새 자료를 제자리에 놓고 지식으로 만든다

LLM Wiki 에서 새 자료가 들어오면 두 가지를 함께 해야 한다 — **파일을 사람이 나중에 찾을 수 있는 자리에 놓기**, 그리고 **그 안의 사실을 위키에 녹여 다음 세션이 읽게 하기**. 한쪽만 하면 위키와 폴더가 서로 어긋나기 시작한다.

이 위키 구조에는 `raw/` 폴더가 없다. 위키 루트 아래 기존 폴더 구조가 곧 원본층이고, 새 파일은 그 구조 안의 **알맞은 폴더**에 들어간다. 그래서 ingest 의 절반은 "어디에 어떤 이름으로 둘까"다.

## ⓪ 위키를 찾고 스키마를 읽는다 — 가장 먼저

작업 폴더(또는 사용자가 말한 경로)에서 위로 올라가며 LLM Wiki 루트를 찾는다: `CLAUDE.md` 에 `llm-wiki:begin` 표시나 "LLM Wiki" 스키마가 있고 `wiki/index.md` 가 있는 폴더.

```bash
# 예: 후보 찾기 (PowerShell 이면 Get-ChildItem -Recurse -Depth 3 -Filter CLAUDE.md)
find . -maxdepth 3 -name CLAUDE.md
```

찾으면 이 순서로 읽는다 — 스키마가 이 스킬보다 우선한다.
1. `CLAUDE.md` 의 LLM Wiki 스키마(특히 **폴더·파일명 관례** 절과 catalog 제외 규칙)
2. `wiki/index.md` → `wiki/overview.md` → `wiki/log.md` 끝부분(`grep "^## \[" wiki/log.md | tail -10`)

못 찾으면 임의로 `wiki/` 를 만들지 않는다. 어느 폴더인지 묻거나, 위키가 없으면 `wiki-setup` 으로 먼저 만들자고 제안한다.

## 왜 검증이 배치보다 먼저인가

받자마자 폴더에 넣으면 그 파일이 우리가 아는 최종본과 다른 판본이어도 모른 채 "확정본" 자리에 앉는다. 계약 날인본이 협상 전 판본이거나, 영수증의 청구 주체가 엉뚱한 법인이거나, 회의록 결정이 위키 서술과 정반대인 일이 실제로 있다. 그래서 순서는 **① 읽고 검증 → ② 자리 정하기 → ③ 배치 → ④ 위키 반영 → ⑤ 스키마 진화 → ⑥ 검증**이다. ①에서 이상을 찾으면 배치 전에 알린다.

## ① 읽고 검증

포맷별 추출은 `scripts/extract.py` 를 쓴다. 파싱 코드를 새로 짜지 않는다. 이 문서의 `scripts/`·`references/` 경로는 **이 스킬 폴더(Base directory) 기준**이니 실행할 때는 절대경로로 부른다.

```bash
python scripts/extract.py "<파일>"                 # 구조 요약 + 텍스트
python scripts/extract.py "<파일>" --render 1,2    # 스캔 PDF·슬라이드 → PNG
python scripts/extract.py "<파일>" --grep 계약금액  # 특정 값 주변만
python scripts/extract.py "<구판.docx>" "<신판.docx>" --diff   # 판본 비교
```

**스캔 PDF 는 텍스트가 안 나온다.** 도장 찍힌 계약서·등록증은 대개 스캔이다. `--render` 로 뽑은 PNG 를 **Read 도구로 직접 눈으로 본다.** OCR 을 붙이지 않는다 — 확인할 건 금액 몇 개와 당사자 이름이고, 보는 게 더 빠르고 정확하다. 텍스트가 제대로 나오는 PDF 면 렌더할 필요 없다.

**검증 = 이미 아는 값과 대조.** 위키에서 같은 대상의 수치·상태를 찾아(`grep`) 맞춰 본다.

대조할 기준값이 위키에 없을 때도 있다 — 막 셋업한 위키, 처음 보는 거래처. 그때는 그 항목을 "⚠️ 대조 불가(기준값 없음)"로 표시하고 사용자에게 묻는다(예: "청구 명의 Example Holdings 가 우리 법인 맞나요?"). 답을 받으면 그 값(우리 법인 정식 명칭·주소, 법인카드 끝자리, 거래처 사업자 정보 등)을 `overview.md` 나 해당 엔티티 페이지에 **기준값으로 적어 둔다** — 다음 ingest 부터는 대조가 된다.

| 자료 | 대조할 것 |
|---|---|
| 계약서·날인본 | 금액(공급가·부가세·합계), 선급·잔금, 기간, 계약일, 당사자 상호·대표, 양측 날인 |
| 검토본(법무 등) | 원본과의 diff 전수(`--diff`), 변경내용 추적·코멘트 |
| 영수증·청구서 | 금액·통화·환율(원화 병기면 역산)·결제일·수단·**청구 대상 명의·주소** |
| 견적서 | 품목·단가·합계·유효기간, 비교견적이면 순위 |
| 회의록·보고서 | 날짜·참석자·결정사항, 위키 서술과 모순되는 부분 |
| 이미지(도장·로고) | 이미 투명 배경인지(→ `references/wiki-rules.md` 투명 PNG), 정말 그 주체의 것인지 |

결과는 항목별 ✅/⚠️ 대조표로 보여준다. "일치합니다" 한 줄로 끝내지 않는다 — 사용자가 자기 기억과 맞춰볼 수 있어야 한다.

**이상을 찾으면** 배치를 멈추지는 않되 응답에서 눈에 띄게 알린다. 판단은 사용자 몫이다. 흔한 유형: 파일명 오타(교정하고 교정했다고 말한다), 청구 주체가 다른 법인, 짝 문서 중 한쪽만 도착(나머지가 왜 필요한지·기한), 같은 이름 기존 파일과 크기·내용이 다름(사람이 고친 판본일 수 있다 — 덮기 전에 diff).

## ② 자리 정하기 — 폴더와 파일명

새 규칙을 발명하지 않고 **이미 있는 관례를 상속**한다. 우선순위:

1. `CLAUDE.md` 스키마의 **폴더·파일명 관례** 표
2. 후보 폴더를 **실제로 열어** 형제 파일의 이름 패턴(접두어·구분자·괄호·날짜 위치까지)
3. `references/naming-patterns.md` 의 일반 패턴

이름만 그럴싸하고 실제 용도는 다른 폴더가 있다(예: `전표/` 인데 영수증 아카이브가 아닌 경우). **열어보고 판단한다.** 마땅한 폴더가 없으면 형제 폴더의 작명을 흉내 내 신설한다 — `인프라/` 안에 `aws 사용내역/` 이 있으면 LLM 영수증은 `인프라/LLM 사용내역/`.

파일명: 위키에 쓰인 **정식 명칭**(약칭·오타 교정), 기존 날짜 관행(`YYYYMMDD` 접미 / `[YYYY]` 접두 등). 업로드 이름이 타임스탬프(`30072026090314.pdf`)나 무의미한 ID(`Receipt2333.pdf`)면 **내용 기반으로 다시 짓는다** — 이 스킬이 있는 이유 중 하나다. 이름에 금액·날짜를 넣을 때는 사람이 그 문서를 부르는 값(충전액·계약금액)과 문서의 기준일(결제일·계약일·회의일)을 쓴다.

폴더 안 파일을 열어볼 수 없어(빈 파일, 권한) 이름만으로 용도를 판단했으면 그렇다고 log 에 적는다.

## ③ 배치

- 받은 파일(다운로드 폴더·첨부 등)을 목적지로 **복사**한다. 받은 위치의 원본 삭제·이동은 사용자가 시킬 때만.
- 목적지에 같은 이름이 있으면: 해시가 같으면 건너뛰고 그렇다고 말한다. 다르면 **멈추고** 차이를 보여준 뒤 선택을 받는다(덮기 / 버전 접미 `_v2` / 취소).
- 위키 루트 안 **기존 원본**은 읽기 전용이다 — 이동·이름변경·삭제는 사용자가 명시할 때만. 시켜서 옮겼다면 그 경로를 가리키는 위키의 `sources:`·링크·catalog 를 `grep` 으로 전수 찾아 함께 고친다.
- 경로에 한글·공백·괄호가 흔하다. 항상 따옴표로 감싸고, PowerShell 에서는 `-LiteralPath` 를 쓴다(`[`·`]` 가 와일드카드로 해석된다).

```powershell
Copy-Item -LiteralPath "$HOME\Downloads\Receipt2333.pdf" -Destination "D:\위키\인프라\LLM 사용내역\[2026]LLM API 크레딧 충전 100USD_20260729.pdf"
(Get-FileHash -LiteralPath "<원본>").Hash -eq (Get-FileHash -LiteralPath "<목적지>").Hash
```

## ④ 위키 반영

세부 규칙(frontmatter·앵커·log·catalog·이력 표기)은 `references/wiki-rules.md` 를 읽는다. 여기서는 판단만.

**먼저 takeaway 를 공유한다.** 무엇을 알게 됐고 위키의 어디가 바뀔지 2~4줄로 말한 뒤 반영한다(Karpathy 패턴의 "핵심을 함께 짚고 나서 쓴다"). 승인을 기다리는 단계는 아니다 — 알리고 바로 진행하되, 사용자가 중간에 바로잡으면 그걸 따른다.

**어디에 쓰는가** — 새 페이지보다 **기존 페이지의 알맞은 절**이 대부분 맞다. 지식이 흩어지면 다음 세션이 못 찾는다. 위키가 아직 비어 있으면 자료의 주제가 되는 개념(또는 엔티티) 페이지 하나를 만들어 시작한다 — 같은 주제의 다음 자료가 그 페이지에 쌓인다.
- 기존 엔티티·개념의 새 사실 → 그 페이지의 해당 절
- 자료 자체가 독립 주제 → `wiki/sources/` 에 신설하고 관련 페이지에서 링크
- 한 자료가 여러 페이지에 걸치는 게 정상이다(거래처·일정·금액·사람). `grep` 으로 같은 대상이 나오는 페이지를 전부 찾아 각각 갱신한다.
- **상태 변화**(드래프트→체결, 미수령→확보)는 그 값이 나오는 **모든 표·문장**을 고친다. 아래에 새 문단만 붙이고 위쪽 표를 낡은 채 두는 게 가장 흔한 모순이다.
- 미결 이슈가 해소되면 그 행을 지우지 말고 `~~이슈~~ ✅ 해소(근거, 날짜)`.
- 반영한 페이지의 frontmatter `sources` 에 새 원본 경로를, `updated` 에 오늘 날짜를 넣는다.

**허브 갱신**: `catalog.md`(해당 폴더 섹션에 등재, 헤더 총계와 늘어난 근거), `index.md`(새 페이지·새 진입점), `overview.md`(진행 상황·미결이 바뀌었을 때만), `log.md` 맨 끝에 append:

```markdown
## [YYYY-MM-DD] ingest | <파일명 또는 주제> — <한 줄 요약>
- 배치: <경로> (원래 이름 → 새 이름)
- 검증: <무엇을 어떻게 대조했나>
- 위키 반영: <페이지 §절>
- ⭐ 부수 발견 / ⚠️ 미결(기한)
```

log 는 다음 세션이 진실원본으로 읽는다. "한 줄"보다 **판단 근거**(왜 그 폴더인지, 무엇을 검증했는지, 무엇이 미결인지)가 남아 있어야 같은 판단을 반복하지 않는다.

앵커 링크(`#...`)는 손으로 짜지 않는다: `python scripts/slug.py "제목"` / `python scripts/slug.py --file <md>`. 제목을 고치면 그 제목을 가리키는 링크가 전부 깨진다.

## ⑤ 스키마 진화

이번 ingest 에서 **새 폴더를 만들었거나 새 명명 관례가 생겼으면** `CLAUDE.md` 스키마의 폴더·파일명 관례 표에 한 줄 추가한다. 스키마는 사용자와 LLM 이 함께 키우는 문서고, 이 한 줄이 다음 ingest 의 판단을 빠르고 일관되게 만든다. 표에 setup 이 남긴 자리표시 행(`_(setup 중 … 채운다)_`)만 있으면 그 행을 첫 관례로 바꾼다. 추가했다고 보고에 적는다. 파일을 열어 보지 못하고 이름만으로 짐작한 관례는 스키마에 적지 않는다.

## ⑥ 검증

린터는 같은 skills 폴더에 함께 설치된 `wiki-lint` 스킬에 있다(`<이 스킬 폴더>/../wiki-lint/scripts/wiki_lint.py`). `--exclude` 에는 스키마 catalog 절의 제외 폴더를 그대로 넘긴다 — 안 넘기면 제외 폴더까지 원본으로 세어 CATALOG 경고가 난다.

```bash
python "<이 스킬 폴더>/../wiki-lint/scripts/wiki_lint.py" "<위키루트>/wiki" --exclude <스키마의 제외 폴더들>
```

- 이번에 고친 페이지에서 🔴(깨진 링크·앵커·frontmatter)가 새로 생기지 않았는지 본다. 기존 이슈는 건드리지 말고 보고만 한다.
- 🔵 데이터 공백은 일부러 남긴 미결 표시(`(미확인)` 등)면 정상이다.
- 배치한 파일은 목적지에서 크기·해시를 다시 읽어 확인한다. 문서 폴더는 Git 이 아닐 수 있으니 커밋을 검증으로 치지 않는다.
- 스크립트가 없거나 실패하면 그 사실을 말하고 `grep` 으로 링크만이라도 확인한다.

## 부분 실행 — 요청을 그대로 읽는다

- "폴더에만 넣어줘" → ①②③⑥. 위키는 건드리지 않고 "위키 반영은 남았다"고 한 줄 알린다.
- "위키에만 반영해줘" → ④⑤⑥ (파일은 이미 제자리)
- "이게 뭔지만 봐줘" → ①
- 파일 없이 말로 준 정보("오늘 상담 다녀왔는데…") → ④⑤⑥. 출처는 `(사용자 전언 YYYY-MM-DD)` 로 적고, 사실과 전언을 구분한다.
- 여러 파일을 한꺼번에 → 파일별로 ①② 를 표로 묶어 먼저 보여주고, 짝 문서·중복을 정리한 뒤 ③④ 를 한 번에. log 항목은 묶음 하나로.

## 응답 형식

작업 후 이 순서로, 짧게:

1. **어디에 뭘 넣었나** — 경로 + 파일명 (이름을 바꿨으면 전→후)
2. **검증 결과** — 대조표 또는 핵심 몇 줄
3. **발견한 것** — 이상·리스크·의외의 사실 (없으면 생략)
4. **위키 어디를 고쳤나** — 페이지·절 한 줄씩, 스키마 관례 추가 여부
5. **미결·다음 액션** — 기한이 있으면 날짜와 함께

파일 내용을 길게 요약하지 않는다. 사용자는 방금 그 파일을 줬고 무엇인지 안다. 사용자가 **모르는 것**(어디에 왜 들어갔나, 대조가 맞나, 무엇이 이상한가)만 말한다.
