# grilling — 계획을 확정할 때까지 묻는 인터뷰

계획·설계의 모든 갈림길을 **한 번에 하나씩** 물어 함께 확정한다. 결정 트리의 가지를 하나씩 내려가고, 앞 답이 다음 질문을 정한다. **서로 합의했다고 확인하기 전에는 계획을 실행하지 않는다** — 이 스킬의 산출물은 코드나 문서가 아니라 확정된 결정 목록이다.

## 묻기 전에 — 스스로 답할 수 있는 건 묻지 않는다

- 코드·문서·설정을 뒤져서 알 수 있는 건 직접 확인한다. 확인한 결과는 질문 대신 한 줄 공유로 바꾼다: "~는 이미 ~로 되어 있어 그대로 씁니다."
- **LLM Wiki 가 있는 폴더면 위키부터 본다** — `CLAUDE.md` 에 LLM Wiki 스키마가 있으면 `wiki/index.md` → `wiki/log.md` 최근 항목 → 관련 페이지. 이미 결정된 것(`결정` 로그), 이전에 기각된 안, 진행 중인 제약을 알고 시작해야 같은 질문을 다시 하지 않는다. 위키와 사용자 말이 어긋나면 그게 첫 질문이다.
- 남은 갈림길을 중요도순으로 세운다. **되돌리기 비싼 결정**(데이터 구조, 외부로 나가는 값, 사용자에게 보이는 계약, 돈·일정)이 먼저다. 사소한 건 마지막에 몰아서 권장안으로 일괄 확인한다.
- 뻔한 질문은 하지 않는다. 숨은 가정을 드러내고, 사용자가 아직 생각 못 한 엣지 케이스와 트레이드오프를 수면 위로 올리는 질문이 이 인터뷰의 가치다.

## 질문 형식 — 첫 번째 심장

**선택지를 만들 수 있는 질문은 `AskUserQuestion` 으로 묻는다.** 평문이면 사용자가 긴 답을 타이핑해야 하지만, 선택지는 클릭 한 번이고 "기타"로 자유 입력도 열려 있다.

- 응답이 없다는 이유로 승인·선택으로 간주하지 않는다.
- **한 번에 질문 1개.** 여러 질문을 묶으면 어리둥절해진다.
- **도구 호출이 곧 질문이다.** 같은 질문·선택지를 평문으로 먼저 쓰고 도구로 또 묻지 않는다 — 두 번 읽게 만드는 벽 텍스트다. 평문에는 배경 브리핑(아래)만 남긴다.
- 선택지 2~4개. **권장안을 첫 번째에 두고 라벨 끝에 "(권장)"**. 권장 이유는 description 에 한 줄.
- 각 선택지 description 은 **결과 중심**으로 쓴다 — "이걸 고르면 화면/데이터/일정/비용이 어떻게 되는지". 구현 방식 나열이 아니다.
- **화면 배치·흐름·데이터 모양이 갈리는 질문은 미리보기를 붙인다.** 말로 설명한 구조 차이는 머리에 그려지지 않는다. 각 option 의 `preview` 필드에 그 안을 골랐을 때 실제로 보게 될 것(가짜 데이터 몇 줄짜리 표, 화면 목업, 목록 예시)을 담는다:

  ```json
  {
    "label": "한 목록으로 통합 (권장)",
    "description": "수리·교환이 시간순 한 줄로 보여 이력을 한눈에 봅니다.",
    "preview": "날짜   | 종류 | 내용\n03-02 | 수리 | 세탁기 소음\n03-09 | 수리 | 같은 건 재방문\n03-15 | 교환 | 신품 교환 완료"
  }
  ```

  preview 로 부족한 흐름 비교는, 시각화 위젯(visualize MCP 의 show_widget)이 있으면 질문 전에 다이어그램으로 보여주고, 없으면 브리핑에 텍스트 표로 대신한다.

자유 서술이 꼭 필요한 질문(이름 짓기, 문구, 우선순위를 말로 듣기)만 평문으로 묻는다.

## 말의 난이도 — 두 번째 심장

질문이 어려워지는 순간 인터뷰는 죽는다. 트리 깊이 들어갈수록 구현 용어로 미끄러지기 쉬운데, **상대는 지금 코드를 보고 있지 않다.**

- 질문의 주어는 "화면에서 / 사용자가 / 데이터가 / 돈이 어떻게 되나"다. 클래스·트랜잭션·컴포넌트·API 경로 같은 구조 용어는 주어가 될 수 없다 — 필요하면 괄호 보조로만.
- 배경 없이 답할 수 없는 질문이면 질문 전에 **2~3문장으로 상황을 쉬운 말로** 깐다. 3문장으로 안 되면 질문이 너무 큰 것이다 — 더 작은 결정으로 쪼갠다.
- **난이도 초과 신호를 보면 즉시 물러선다.** 답이 짧아지거나("어…", "글쎄"), 반문이 오면("그게 무슨 말이야?") 같은 질문을 같은 어휘로 반복하지 말고, 더 쉬운 말 + 실제 도메인 값(주문 1건, 고객 한 명, 금액 하나)으로 된 예시로 **다시 구성해서** 묻는다.

## 진행 관리

- 5문항 안팎마다 지금까지 확정된 것을 쉬운 말로 3~5줄 요약하고 이어간다. 사용자가 어디까지 왔는지 놓치지 않게.
- 답이 앞선 결정과 충돌하면 바로 짚는다: "아까 A 로 정했는데 지금 답은 B 쪽이라 둘 중 하나를 바꿔야 합니다."
- 사용자가 "그만", "충분해", "나머진 알아서"라고 하면 남은 갈림길을 권장안으로 채운 목록을 보여주고 그대로 갈지 묻는다.

## 끝날 때 — 확정 목록과 승인

1. 확정된 결정 전체를 한 번에 보여준다. 결정마다 **무엇을 · 왜(사용자가 고른 이유) · 기각한 대안**. 미결로 남긴 것은 따로.
2. 선택지로 승인을 받는다: 진행 (권장) / 수정할 것 있음 / 처음부터. **승인 전에는 실행하지 않는다.**
3. 승인되면 결정을 어디에 남길지 묻는다(권장안 먼저):
   - **LLM Wiki 가 있으면** — `wiki/log.md` 맨 끝에 `## [YYYY-MM-DD] 결정 | <주제> — <한 줄>` 항목(결정·이유·기각안·미결)을 append 하고, 결정이 바꾸는 위키 페이지(현재 상태·계획 절)를 갱신한다. 위키 규칙은 `wiki-ingest` 스킬을 따른다.
   - 코드 저장소면 — 사용자가 정한 문서(PRD, 설계 문서, ADR 등)에.
   - 남기지 않음 — 대화 안 정리로 끝.

## 하지 않는 것

- 확정 전에 코드·문서를 만들기 시작하지 않는다.
- 한 번에 여러 질문, 권장안 없는 질문, 코드에서 확인 가능한 질문을 하지 않는다.
- 사용자의 답을 내 권장안 쪽으로 끌고 가지 않는다 — 권장안은 근거와 함께 한 번 제시하고, 사용자가 다르게 고르면 그 결정을 존중해 다음 가지로 간다.
