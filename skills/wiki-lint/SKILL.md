# wiki-lint — 위키 건강검진

기계가 확실히 잡을 것과 LLM 이 읽고 판단할 것을 나눈다. 스크립트는 잡일이고, **진짜 가치는 ② 판단과 ④ 다음 질문**에 있다. 스크립트만 돌리고 끝내지 않는다.

## ⓪ 위키를 찾고 스키마를 읽는다

작업 폴더에서 위로 올라가며 `CLAUDE.md` 에 LLM Wiki 스키마(`llm-wiki:begin` 표시 등)가 있고 `wiki/index.md` 가 있는 루트를 찾는다. 스키마의 **catalog 제외 규칙**과 린트 기준을 읽는다 — 스키마가 이 스킬보다 우선한다. 위키가 없으면 `wiki-setup` 을 제안한다.

## ① 기계 점검

스크립트 경로는 이 스킬 폴더(Base directory) 기준이다. `--exclude` 에는 스키마 catalog 절의 제외 폴더를 넘긴다.

```bash
python scripts/wiki_lint.py "<루트>/wiki" --exclude <스키마의 catalog 제외 폴더들>
python scripts/wiki_lint.py "<루트>/wiki" --stale-value "옛 금액" "옛 벤더명"   # 바뀐 값이 남았나
python scripts/wiki_lint.py "<루트>/wiki" --skip-raw     # 원본이 아주 많아 느릴 때
```

| 표시 | 항목 | 의미·조치 |
|---|---|---|
| 🚨 | CONFLICT | 동기화 충돌 사본 — **최우선**, ③ |
| 🔴 | BROKEN-LINK / BROKEN-ANCHOR | 대상 페이지·제목 없음. 제목을 고치면 앵커가 깨진다. 새 앵커는 `wiki-ingest` 의 `scripts/slug.py` 로 계산 |
| 🔴 | FRONTMATTER | 누락·필드 없음·날짜 형식 |
| 🟡 | DUP-HEADING | 같은 페이지 중복 제목 — 두 번째부터 앵커가 `-1` |
| 🟡 | RAW-LINK / SOURCE-MISSING | 위키가 가리키는 원본 경로가 없음 — 원본이 옮겨졌거나 오타. 실제 위치를 찾아 경로를 고친다 |
| 🟡 | ORPHAN / UNREACHABLE | 들어오는 링크 0 / index 에서 닿지 않음 — index 나 관련 페이지에서 링크 |
| 🟡 | LOG | log 머리 형식 위반, 날짜 역행(중간 삽입 의심) |
| 🟡 | CATALOG | 헤더 총계 ≠ 실제 원본 수, 파일명이 catalog 에 없는 원본(폴더별 개수 — 요약 등재 폴더면 정상) |
| 🟡 | INGEST-PENDING | `log.md` 마지막 저장 이후 수정된 원본 = ingest 가 밀렸을 가능성 |
| 🟡 | STALE | `updated` 가 오래된 페이지 (`--stale-days`, 기본 180) |
| 🔵 | GAPS | `(미확인)`·`확인 필요`·TBD·미정 이 많은 페이지 |

종료코드 1 = 🚨/🔴 있음. CATALOG 총계 차이는 제외 규칙이 달라서일 때가 많다 — 스키마의 제외 목록을 `--exclude` 로 맞춘 뒤 다시 본다. 스크립트가 없거나 실패하면 `grep` 으로 대신하되 그 사실을 말한다.

## ② 판단 — 여기가 본론

위키를 실제로 읽는다. `index.md` 부터, 그다음 `log.md` 최근 항목, 그다음 금액·일정·상태가 많은 페이지 순으로.

**모순** — 두 페이지가 같은 사실에 다른 말을 하는가. 특히 금액·인원·날짜·상태·담당자. 발견하면 영향(돈·일정)을 따져 미해결 목록에 올린다.

**낡음(stale)**
- 견적·조건의 유효기간이 지났는가, 지나간 일정이 아직 "예정"으로 남았는가
- 새 원본이 이전 정보를 무효화했는데 옛 페이지가 그대로인가 — `log.md` 의 최근 ingest 가 고쳤어야 할 페이지를 다 고쳤는지 본다
- **표의 상태 칸이 본문과 어긋나는가** — 아래에 새 문단만 붙이고 위쪽 표를 낡은 채 둔 경우가 가장 흔하다
- 파생 수치(D-day, 합계, 소진율, 남은 금액)가 실제와 맞는가

**구조**
- 누락 엔티티 — 여러 페이지에 나오는데 자기 페이지가 없는 사람·조직·시스템·개념
- 크로스링크 누락 — 관련 있는데 서로 링크가 없는 페이지
- 요약 미갱신 — 사례 표에 행은 늘었는데 요약·`배운 것`·overview 가 그대로
- overview.md 가 지금 상황을 반영하는가

**데이터 공백** — 비교표의 빈 칸, 확인 안 된 조건, 근거 없이 추정으로만 남은 숫자. 영향이 큰 것부터. 웹 검색이나 사용자 한마디로 채울 수 있는 것이면 그렇다고 적는다.

## ③ 충돌 사본 병합

`… (○○님과 충돌하는 사본).md`·`(conflicted copy)` 를 발견하면 **다른 작업보다 먼저** 처리한다.

1. 원본과 충돌 사본을 **둘 다** 읽고 차이를 뽑는다
2. **양쪽 변경을 병합한다** — 한쪽을 버리지 않는다. 상대가 쓴 내용이다
3. 같은 줄을 서로 다르게 고쳐 어느 쪽이 최신인지 애매하면 사용자에게 묻는다
4. 병합 결과를 원본에 쓰고, 충돌 사본은 삭제하지 말고 `wiki/_to_delete/` 로 옮긴 뒤 사용자에게 알린다(지우는 건 사용자 몫)
5. `log.md` 에 `## [YYYY-MM-DD] 수정 | 충돌 사본 병합 — <파일>` 기록

## ④ 보고

대화로 보고한다. 별도 리포트 파일을 위키에 쓰지 않는다 — 위키가 지저분해진다.

1. 🚨 **지금 처리할 것** — 충돌 사본, 지난 시한, ingest 밀린 원본
2. 🔴 **영향이 큰 미해결** — 금액·리스크 큰 순
3. 🟡 **구조 문제** — 깨진 링크·고아·미등재 (개수 + 대표 예 몇 개)
4. 💡 **다음에 알아볼 것 3개 이내** — 이게 린트의 가장 큰 산출물이다. "확인 필요 22건"보다 "이번 주에 이 3개를 물어보면 된다"가 쓸모 있다. 누구에게·무엇을 물을지까지.

## ⑤ 수정은 동의를 받고

린트는 자동 수정 도구가 아니다. **사용자가 동의한 것만 고친다.**

묻지 않고 고쳐도 되는 것 (기계적이고 대상이 분명한 것):
- 새 페이지를 `index.md`·`catalog.md` 에 등재
- 대상이 분명한 깨진 링크·앵커 (앵커는 `slug.py` 로 계산)
- 파생 수치 재계산 (D-day, 합계)

그 외 — 특히 **내용 판단이 들어가는 수정**(모순 해소, 낡은 값 교체, 페이지 신설·병합)은 확인받는다. 무엇을 고쳤든 고치지 않았든 마지막에 `log.md` 에 남긴다:

```markdown
## [YYYY-MM-DD] lint | 🔴 N · 🟡 N · 💡 <다음 질문 요약>
- 고친 것: …
- 남긴 것(사용자 판단 대기): …
```
