# wiki-setup — 폴더를 LLM Wiki 로 만든다

Karpathy 의 LLM Wiki 패턴(원본 · 위키 · 스키마 3계층)을 **기존 폴더 위에** 세운다. 원안과 이 묶음의 차이는 `references/llm-wiki-pattern.md` — 핵심은 두 가지다.

- **`raw/` 폴더를 만들지 않는다.** 사람이 쌓아 온 폴더 구조가 곧 원본층이다. 원본을 옮기지 않는다.
- **스키마(`CLAUDE.md`)에 "세션 시작 시 무조건 위키부터" 규칙을 넣는다.** 이 규칙이 없으면 다음 세션이 위키를 건너뛰고 원본부터 뒤져, 쌓은 결론을 버리고 옛 정보를 다시 말한다. 이 규칙은 셋업의 필수 산출물이다.

## ⓪ 대상 확정과 기존 상태 확인

1. 대상 폴더: 사용자가 말한 경로, 없으면 현재 작업 폴더. 홈 디렉터리·드라이브 루트·코드 저장소 루트처럼 범위가 넓거나 애매하면 정확한 경로를 확인받는다.
2. 이미 위키가 있는지 본다 — `wiki/index.md`, `CLAUDE.md` 안의 `llm-wiki:begin` 표시.
   - 둘 다 있으면 셋업이 아니다. "이미 LLM Wiki 다"라고 말하고 `wiki-lint` 로 점검하거나 빠진 파일만 보충할지 묻는다.
   - 일부만 있으면(예: `wiki/` 는 있는데 스키마 블록이 없음) 없는 것만 만든다. `scaffold.py` 는 있는 파일을 덮지 않는다.

## ① 짧은 인터뷰 — 스캔으로 알 수 없는 것만

먼저 스캔한다. 폴더를 보면 알 수 있는 건 묻지 않는다.

```bash
python scripts/inventory.py "<대상>"                      # 폴더별 개수·용량·확장자
```

그다음 한 번에 하나씩, 권장안을 붙여 묻는다(`AskUserQuestion` 선택지로). 보통 3~4문항이면 충분하다.

1. **위키 이름과 한 줄 도메인** — 예: "영업팀 업무 — 거래처 계약·견적·정산 문서". 폴더명·내용에서 추정한 안을 권장안으로.
2. **원본 집계에서 뺄 폴더** — 스캔에서 보인 도구·산출물·임시 폴더(스킬, 빌드 결과, 캐시, LLM 이 만든 산출물)를 후보로 제시.
3. **함께 편집하는 사람·도구** — 혼자 / 동기화 폴더(Google Drive·Dropbox)로 여럿. 여럿이면 스키마에 충돌 사본 병합 규칙을 강조한다.
4. (원본이 많을 때) **초기 구축 범위** — overview 만 / overview + 핵심 엔티티·개념 몇 개 / 폴더 묶음별 단계 구축.

## ② 골격 생성

```bash
python scripts/scaffold.py "<대상>" --name "<위키 이름>" --domain "<한 줄 도메인>" --exclude <제외 폴더들> --dry-run
python scripts/scaffold.py "<대상>" --name "<위키 이름>" --domain "<한 줄 도메인>" --exclude <제외 폴더들>
```

dry-run 결과를 먼저 보여준다. 만드는 것:

- `wiki/index.md` · `overview.md` · `log.md`(첫 `setup` 항목) · `catalog.md`(원본 인벤토리 자동 집계) · `entities/` · `concepts/` · `sources/`
- `CLAUDE.md` — 없으면 새로 만든다. **이미 있으면 기존 내용을 보존하고 첫 제목 아래에 LLM Wiki 블록을 끼워 넣는다.**
- 블록은 `<!-- llm-wiki:begin -->` … `<!-- llm-wiki:end -->` 로 감싸여 다시 실행해도 중복되지 않는다.

블록에 들어가는 내용(`assets/CLAUDE.block.md`): §0 세션 시작 규칙(무엇을 하든 index → overview → log 끝부분 → 주제 페이지 → 부족할 때만 원본), §1 3계층(raw 폴더 없음), §2 페이지 규칙, §3 일상 운영 스킬, §4 Ingest·Query·Lint, §5 log 형식, §6 catalog 규칙, §7 폴더·파일명 관례 표, §8 추출 도구.

## ③ 스키마를 이 폴더에 맞게 채운다

템플릿을 그대로 두지 않는다. 특히 **§7 폴더·파일명 관례 표**가 이 위키의 ingest 품질을 좌우한다.

- 원본이 많은 폴더 몇 개를 실제로 열어 파일명 패턴을 관찰한다(접두어 `[YYYY]`·`(본견적)`, 구분자 `_`, 날짜 위치, 판본 `_vN`, 확정 표시 `[完]` 등).
- 자료 유형 → 폴더 → 파일명 패턴 → 실제 예 를 표로 채운다. 관찰한 것만 적고 발명하지 않는다. `wiki-ingest` 의 `references/naming-patterns.md` 에 일반 패턴이 있다.
- 이름과 실제 용도가 다른 폴더(예: `전표/` 인데 영수증 보관처가 아님)를 발견하면 그것도 적는다.
- 사용자 맞춤 규칙(답변 언어, 용어 원어 유지, 대외비 폴더 취급 등)이 인터뷰에서 나왔으면 블록 위쪽에 짧게 넣는다.
- 기존 CLAUDE.md 에 블록을 끼워 넣었다면 기존 규칙과 충돌하는 곳이 없는지 읽어 보고, 충돌하면 사용자에게 어느 쪽을 따를지 묻는다.

## ④ 초기 구축 — 위키에 첫 지식을 넣는다

빈 골격만 남기면 다음 세션이 읽을 게 없다. 인터뷰에서 정한 범위만큼:

1. **overview.md** — 원본을 폴더 단위로 훑어(파일명·대표 문서 몇 개를 `wiki-ingest` 의 `scripts/extract.py` 로) 범위·주요 주체·현재 진행 상황·미결을 한 페이지로.
2. **핵심 엔티티·개념 몇 개** — 여러 폴더에 반복해 나오는 사람·조직·시스템·주제. frontmatter `sources` 에 근거 원본 경로.
3. **index.md** — 만든 페이지를 등재.
4. 원본이 수백 개 이상이면 한 번에 다 하지 않는다. 폴더 묶음 단위로 나눠 하나씩 진행하고, 묶음마다 takeaway 를 사용자와 짚는다. 남은 묶음은 log 의 setup 항목에 "다음 ingest 대상"으로 적는다.

## ⑤ 검증

`scripts/` 는 이 스킬 폴더 기준, 린터는 같은 skills 폴더의 `wiki-lint` 스킬에 있다.

```bash
python ../wiki-lint/scripts/wiki_lint.py "<대상>/wiki" --exclude <제외 폴더들>
grep -n "llm-wiki:begin\|세션 시작" "<대상>/CLAUDE.md"
```

- 린트 🔴 0건, catalog 헤더 총계 = 실제 원본 수.
- **CLAUDE.md** 에 블록과 §0 세션 시작 규칙이 들어갔는지 확인한다. 빠지면 셋업 미완료다.
- 기존 CLAUDE.md 에 끼워 넣은 경우, 블록 바깥의 원래 내용이 그대로인지 본다.

## ⑥ log 와 보고

`log.md` 의 첫 `setup` 항목에 이번 셋업에서 정한 것(이름·도메인·제외 폴더·관찰한 관례 수·초기 구축 범위·다음 ingest 대상)을 덧붙인다.

보고는 짧게:
1. 만든 것·끼워 넣은 것 (경로)
2. 원본 집계 (총 N개, 제외한 것)
3. 스키마에 적은 관례 요약
4. 초기 구축한 페이지와 남은 것
5. 다음 단계 — "새 파일은 `wiki-ingest`, 주기 점검은 `wiki-lint`"

## 하지 않는 것

- 원본 파일을 `raw/` 등으로 옮기거나 이름을 바꾸지 않는다.
- 기존 `CLAUDE.md`·위키 파일을 덮어쓰지 않는다(끼워 넣기만).
- 관찰하지 않은 관례를 스키마에 적지 않는다.

## 참고 파일

- `references/llm-wiki-pattern.md` — Karpathy 원안 요지와 이 묶음의 변형(왜 raw 가 없나, 왜 catalog 가 있나)
- `assets/CLAUDE.block.md` — 스키마 블록 템플릿
- `scripts/inventory.py` — 원본 인벤토리·catalog 초안
- `scripts/scaffold.py` — 골격·스키마 블록 생성 (멱등, 덮어쓰지 않음)
