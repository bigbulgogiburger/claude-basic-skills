## 0. 세션 시작 — 무엇을 하든 LLM Wiki 를 먼저 찾는다

이 폴더는 **LLM Wiki**({{NAME}})로 운영된다. 질문에 답하거나, 파일을 찾거나, 문서·코드를 만들기 **전에 반드시** 아래 순서로 위키부터 읽는다. 사용자가 위키를 언급하지 않아도, 질문이 사소해 보여도 마찬가지다.

1. `wiki/index.md` — 내비게이션 허브. 관련 페이지 진입점을 여기서 찾는다.
2. `wiki/overview.md` — 이 위키가 다루는 것 한눈에.
3. `wiki/log.md` — **끝에서부터 역순으로** 최근 항목을 읽는다(`grep "^## \[" wiki/log.md | tail -10`). 진행 중인 일·최근 결정·미결 이슈는 여기가 진실원본이다.
4. 주제에 맞는 `wiki/entities/`·`wiki/concepts/`·`wiki/sources/` 페이지 → 그래도 부족할 때만 원본 파일.

왜: 위키는 이전 세션들이 원본을 읽고 정리·정정해 둔 결론이다. 위키를 건너뛰고 원본부터 뒤지면 같은 조사를 반복하고, 이미 정정된 옛 수치를 다시 말하게 된다.

- 위키에 답이 없으면 "위키에 없음"을 먼저 말하고 원본을 찾는다. 원본에서 새로 알게 된 것·재사용할 만한 분석은 위키에 환원한다(아래 §4 Query).
- 시작할 때 오늘 날짜와 `log.md` 최신 항목 날짜의 간극을 본다. 간극이 크고 새 원본이 들어와 있으면 ingest·lint 가 밀린 것이다 — 사용자에게 알린다.

## 1. 3계층 구조 (Karpathy LLM Wiki)

1. **원본 소스 (읽기 전용)** — 이 폴더에 이미 있는 업무 파일 전부. **별도 `raw/` 폴더는 없다** — 기존 폴더 구조가 곧 원본층이다. 기존 원본은 읽기만 하고 수정·이동·이름변경·삭제하지 않는다(사용자가 명시적으로 시킬 때만). 새로 받은 파일은 ingest 때 관례에 맞는 폴더에 **배치**한다.
2. **위키 (`wiki/`)** — LLM 이 만들고 고치는 마크다운 지식베이스. LLM 이 전적으로 소유한다.
3. **스키마 (이 블록)** — 위키 구조·관례·워크플로. 사용자와 LLM 이 함께 고쳐 나간다. 새 관례가 생기면 여기(§7)에 적는다.

```
{{NAME}}/
├─ CLAUDE.md             ← 스키마 (이 블록)
├─ wiki/
│  ├─ index.md            ← 내비게이션 허브 (먼저 읽기)
│  ├─ overview.md         ← 한눈에 보기
│  ├─ log.md              ← 시간순 작업 로그 (append-only)
│  ├─ catalog.md          ← 원본 파일 인벤토리 (폴더별)
│  ├─ entities/           ← 사람·조직·시스템·거래처 등 "누구/무엇"
│  ├─ concepts/           ← 주제·절차·구조·비교 등 "어떻게/왜"
│  └─ sources/            ← 개별 원본 심층 요약 (필요할 때만)
└─ (그 외 기존 폴더 = 원본 소스)
```

## 2. 페이지 작성 규칙

- 모든 페이지는 마크다운, 파일명은 한국어 허용(`entities/거래처-A사.md`).
- 허브(`index`·`overview`·`log`·`catalog`) 외 페이지는 frontmatter 3필드를 둔다:
  ```yaml
  ---
  type: entity | concept | source
  updated: YYYY-MM-DD
  sources: ["폴더/파일.pdf"]   # 근거 원본 경로(루트 기준)
  ---
  ```
- 다른 페이지는 상대 링크 `[표시명](../concepts/주제.md)`. 엔티티·개념이 처음 나오면 링크를 건다. 앵커(`#...`)는 GitHub slug 규칙 — 손으로 짜지 말고 `slug.py` 로 계산한다.
- 사실·수치에는 근거 원본 경로를 적는다: `(출처: 폴더/파일.pdf)`.
- 원본에서 확인한 사실과 LLM 의 추론을 구분한다. 자료끼리 충돌하면 ⚠️ 와 양쪽 출처를 남긴다.
- 값이 바뀌면 현재 값으로 고치되 이력을 남긴다: `~~구값~~ → **신값** (사유, 날짜)`. 상태가 바뀌면 그 값이 나오는 **모든 표·문장**을 함께 고친다.

## 3. 일상 운영 — 스킬

| 할 일 | 스킬 | 언제 |
|---|---|---|
| 새 자료 넣기 | `wiki-ingest` | 파일을 받았거나 말로 새 정보를 줬을 때 — **파일을 받으면 이것부터** |
| 건강검진 | `wiki-lint` | 주기적으로, 또는 "위키 점검" 요청 시 |
| 계획 확정 인터뷰 | `grilling` | 계획·설계를 굳히기 전 |

## 4. 워크플로

### Ingest
원본을 읽고 검증 → 핵심 takeaway 를 사용자와 공유 → 관례에 맞는 폴더·파일명으로 배치 → 관련 entities/concepts 갱신(한 원본이 여러 페이지에 걸칠 수 있다), 필요하면 `sources/` 신설 → `catalog.md`·`index.md` 갱신 → `log.md` append.

### Query
`index.md` 에서 관련 페이지를 찾아 읽고, 필요하면 원본까지 확인해 출처와 함께 답한다. **좋은 답은 위키에 환원**한다 — 새로 만든 비교·분석·연결은 `concepts/` 나 `sources/` 페이지로 남겨 지식이 쌓이게 한다.

### Lint
페이지 간 모순, 새 원본 때문에 낡은 진술, 고아 페이지, 페이지가 필요한데 없는 개념, 빠진 상호 링크, 카탈로그와 실제 원본의 불일치를 점검하고 `log.md` 에 기록한다.

## 5. log.md 형식

append-only — **맨 끝에만** 추가하고 기존 항목은 고치지 않는다.

```
## [YYYY-MM-DD] <종류> | <한 줄 요약>
```

종류: `setup` · `ingest` · `query` · `수정` · `결정` · `lint` · `변경`. 본문에는 다음 세션이 판단 근거를 알 수 있게 바뀐 수치(전→후), 검증한 것과 방법, 부수 발견(⭐), 미결(⚠️, 기한), 고친 페이지를 적는다.

## 6. catalog.md 규칙

- 원본 파일을 폴더별로 등재하고 헤더에 총계와 갱신 이력을 둔다. 총계를 바꿀 때는 무엇이 몇 개 늘었는지 근거를 함께 적는다.
- 집계 제외: `wiki/`, `CLAUDE.md`, `AGENTS.md`, Office 임시(`~$`·`.~lock`){{EXCLUDES}}.
- 무효가 된 원본은 지우지 말고 `~~파일명~~ ⛔무효` 로 표시한다(실물이 디스크에 남아 있으므로).
